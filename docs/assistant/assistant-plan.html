What this changes in the design

An assist contract (new)

Assist means minimal, in place, fast: keep the position, size, pose and layout; improve the strokes you made rather than replacing the drawing; never add content unasked. A bigger change needs a marker (**!) or a question first.

Speed: your targets (decided)

Small pieces (a few words, a simple shape, a formula): a few seconds is fine. The input is small, so the model is quick. Big tasks (*c! commands, **!, diagrams from a peer): they may take long. Never silently: thinking is always visible where it happens. Geometric touch-ups (smoothing, snapping) can still be instant in the app; that's a bonus, not a must.

Auto-improve toggle (decided)

A toggle button in the toolbar (plus a shortcut and a menu entry). On: the assistant improves everything you write, unasked (formulas → LaTeX, text in your handwriting, diagrams, consistent colours). Off: only your markers and commands are acted on. Its dropdown switches the individual rules (formulas / text / diagrams / colours). The status strip always shows which mode is on.

Visible thinking (new, first-class)

Every piece of work the assistant is doing shows on the canvas: the zone is highlighted (a soft animated outline around the region or next to the marker), with a small thinking icon and a one-line status ("reading formula…", "asking andrew-proj-fd…", "drawing 3/5"). Queued, thinking, drawing, done or failed, each visibly. Tap the icon to cancel or see details. The status strip counts what's in progress.

Markers are the command grammar

Your five markers are built in (and extendable). The app finds candidate markers cheaply (an asterisk is 2–4 short crossing strokes, "!" is a bar plus a dot) and asks the fast model only to read the tiny crop. It wakes the companion with "*w! next to the pigeon on page 1", and removes the marker when it's done.

Context that lasts all day

The companion keeps images out of its context (crops on demand, summaries in the notes memory), and before the context runs out it rolls over: a fresh session resumed from a canvas-state summary. The app watches, so a rollover loses nothing.

Delegation as a default

The companion renders and watches. Facts, verification and docs are asked of the project session. Peer messages are data: they never grant permissions (as andrew-proj-fd already did right: push only on your confirmation).

Drawings into docs, correctly

"Publish this page to the project docs" exports from the app's renderer (nothing missing), and the peer commits it on your confirmation. That's the path your 11 schemes took, made reliable.

0. Scope: a Linux prototype on your subscriptions

What xournalai is for you: a shared whiteboard between you, your Claude sessions and your system. Three flows:
① Assisted drawing (phase 1, tested first). You draw; a Claude session helps: strokes, shapes, colours, sketches, images, formulas.
② Sessions and your system draw for you. Start a board already connected: "draw the architecture of the project in this folder" (the project session knows it), "learn my system and plot CPU and memory, capacity and current use, hand-drawn". Knowledge and live data become drawings you can then work on.
③ The drawing as a launchpad. What's on the page starts or feeds work in other sessions: implementation, research, tinkering, or continuing a running conversation.
The flows mix freely in one session: a diagram a project session drew (②) that you annotate with help (①) becomes the task for the next step (③).
Now: a complete, stable xournalai on your Linux laptop, for daily use and for pitching. Installed with one command, with no terminal window. The assistant runs on your Claude or Codex subscription through the locally installed Claude Code, Codex or OpenCode. No API keys, no tokens bought separately, no servers of ours.
Later, not in scope: a public endpoint or service, the built-in API runner, Android, macOS, public packaging. The architecture keeps those doors open, and nothing is built for them now.

What this changes in the plan

  • The runner is ACP only, with the local CLIs. The built-in API runner moves to the later horizon.
  • Installing it is part of the product: one script builds, installs, registers the launcher and sets up the ACP adapters in a private folder the app manages. The app checks the setup and says what's missing.
  • Stability comes before features. Agent crashes and hangs must never freeze or break the app (see 5.9). Usage is yours to judge (Max plan); the app only shows what it spends.
  • Android and other platforms: a separate, later iteration with its own redesign. Not discussed here.
  • Voice A (push-to-talk) uses local speech recognition only (whisper.cpp), with no cloud; if it's in, it's in the prototype.
  • The terminal drawer is dropped from the prototype. You don't want a terminal; the Activity panel replaces it.

Architecture that keeps the doors open (without building them)

  • Assistant core as a plain C++ library, with no GTK: intents and queue, action library, work-unit grouping, runner interface, ACP client, prompts. The GTK app is one front end; an Android or macOS front end would be another.
  • A runner interface with a remote-capable protocol: intents and results are serialisable messages, so a "remote runner" (laptop serving phone, later a cloud endpoint) is a transport, not a redesign.
  • MCP stays the tool surface: any front end that implements the tools can be driven by the same runners.

0.1 The scenario: how you'll use it

  1. Think with a pen. You open xournalai to brainstorm something and start drawing.
  2. Assistant on. You switch on AI mode. It watches (the focused way: fresh pieces and zones) and helps: tidier strokes, clean shapes in hand-drawn diagrams, colours, drawing what's tedious by hand, improving pictures.
  3. Ask as you go: "help with this schema", "colorize this", "draw a server rack here", "find a photo of X and put it here" (web search, image insert), "generate an illustration of Y" (image generation). You keep drawing while it works.
  4. It talks to your other sessions. Your software-engineering session lives in the project folder with its CLAUDE.md, skills and the work in progress. The drawing session asks it for context ("which modules talk to the broker?") and draws with the answer. The project session can push to the canvas too ("put the new architecture on page 4"). What you draw becomes a task for the project session, with the picture attached.
  5. Connected from the start. A board can begin linked to a project session or folder: "draw the system architecture of the project in ~/workspace/andrew_proj" (the drawing session asks the project session, which knows the code), or "learn my laptop and draw CPU and memory: capacity and current utilisation, as hand-drawn charts" (the drawing session uses Claude Code's own tools to inspect the system). The result is a drawing you then refine and talk about (0.5).
  6. From drawing to action (the launchpad). When the drawing is in good shape, it seeds further work: "start implementing this" in a new or existing project folder, "research this", "tinker with this idea", or "continue with andrew-proj-fd from here". The receiving session gets the picture and its meaning (transcribed text, diagram structure, open questions) and can report progress back onto the page (0.4).
  7. Division of labour. The drawing session knows the canvas, drawing skills and tools. The project sessions know their code. Neither has to know everything, and each keeps the full power of Claude Code.

The consequence for the design: xournalai's assistant is a real, full Claude Code session, embedded and hidden but complete (tools, skills, web, MCP, subagents, peer messaging), specialised for drawing through its workspace, and a peer among your sessions.

0.2 Anatomy of the assistant session

Workspace

~/.local/share/xournalai/assistant/ (or per document): its own CLAUDE.md ("you are the drawing assistant of xournalai…"), the drawing skills (xournal-conspect and new ones), the action library, and an exchange folder for images shared with other sessions.

Tools

xournalai's MCP (per-window socket), plus everything your Claude Code has: web search and fetch, files, bash, subagents, peer messaging, and whatever image generation you've wired in (Nano Banana, an Anthropic tool, …). xournalai only has to bring the images onto the canvas well.

One session, helpers inside

The main session (strong model) holds the conversation. A canvas-watcher helper agent on a fast model processes the fresh pieces; others as needed (layout, image search). This replaces "two sessions per document": one context, and a cheap model where it belongs.

A peer on the bus

Named xournalai-<document>. It messages project sessions and answers them. Pictures travel as files in the exchange folder (same laptop), referenced in the message.

Hidden, but yours

No terminal by default. "Open session in terminal" starts claude --resume <id> in your normal terminal to take over, inspect or debug. There's nothing to embed, and it replaces the VTE drawer.

Lifecycle

Starts when AI mode is switched on (or on the first request), stays while the document is open, resumes the same session next time (its memory of this document lives on). A pause stops it acting at once.

Where I push back

"Sees completely what I'm doing" has to mean a cheap, focused eye. If the full main session (strong model, big context) looks at every stroke, it gets slow and your conversation context fills with ink. The fast canvas-watcher helper looks at the fresh pieces and passes only meaningful events up ("a diagram of 5 boxes appeared at the top-left"). The main session stays for thinking and talking.
Talking to other sessions takes time and it's asynchronous. A question to the project session can take a minute. The app must never wait: the Activity panel shows "asked andrew-proj-fd, waiting", you keep drawing, and the answer arrives as a note or draft.

0.3 Lessons from your canvas session

From the session that drew Einstein, coloured your butterfly and flower as you drew them, redrew your diagrams, typeset formulas, wrote in your handwriting (Russian and English) and built the fleet architecture pages with andrew-proj-fd. Its record: 149 waits for your edits, 116 SVG imports, 85 renders, 45 LaTeX formulas, 64 deletions.

What happenedWhat it means for the design
104 tool results were too big for the agent (e.g. an SVG import answering with ~200k characters: every stroke's id and bbox). Compact answers by default: count, operation id and overall bbox; ids only on request or written to a file. A quick win, fixable now.
An SVG over the 5 MB limit had to be split by hand. Big drawings go by file path, streamed and chunked by the app, with no size ceiling for local files. A quick win.
Its scripts wanted direct canvas access (fetch strokes, place glyphs) but had no sanctioned way (a token in a config file). A canvas SDK for the assistant's scripts: a small Python module plus a CLI that talk to the per-window socket (owner-only permissions, no token), so skills like your handwriting library can work fast and directly.
Procedural drawing couldn't reach a likeness of Einstein; tracing a photo into line art could. Image → native strokes as an app tool: trace_image(image, style: line-art | pencil | contour, detail) turns any picture (found on the web, generated, photographed) into editable pressure strokes. That covers your "sketch it with native strokes" wish for anything with a reference.
Your handwriting was captured into a glyph library inside the skill and reused, with fixes (dots on "i", "g" and "p"). "My handwriting" as a first-class feature: capture and refine your glyphs in the app, plus a tool write_handwritten(text, x, y, size, tidy). Every session can then write in your hand, not just this skill. A strong pitch feature.
Grouping text into lines went wrong once (a heading and the next line mixed up; a tilted baseline). Line and word grouping belongs in the app's layout analysis (it exists; make it robust to slant and mixed scripts), so the model doesn't redo it every time.
Command markers you invented: XC! (revise), *r! (generate an image). Keep them. Your markers are first-class: defined in the action library (marker → action), found cheaply among the fresh pieces, next to the AI pen. *r! is served by whatever image tool your session has.

The peer caught a mistake (a service is in prod, not only dev) before anything was published. Validates the bus design: "verify with project session" becomes a built-in step for technical diagrams.
An export left out a sketch that had been drawn separately. Exports and "send page to session" always come from the app's own renderer of the whole page (layers included), never from a composite made by the agent.
Connection drops, the invisible pause Fixed already: the bridge keeps the tools across restarts, the port is taken over, the pause is obvious.

0.4 The launchpad: from a drawing to sessions

Phase 2, built on phase 1. A page (or a region) becomes the starting point of real work elsewhere.

Start a new session from the page

"Start implementation", "Start research", "Tinker", or your own templates. You choose a folder (new or existing project); a Claude Code session starts there with a handoff package and a first prompt. It opens in a normal terminal window (that's where you work with project sessions), joins the bus, and is linked to the page.

Continue with a running session

Send the page or a region to a peer (andrew-proj-fd, …) with an instruction: "update the fleet docs from this", "does the code match this diagram?". Replies land as notes or drafts.

The handoff package

Built by the drawing session so the receiver doesn't guess: the page image (from the app's renderer), transcribed handwriting, diagram structure (boxes, arrows, labels as a graph), formulas as LaTeX, the notes memory, open questions, and the link back. Saved in the exchange folder and referenced in the prompt.

The round trip

Linked sessions can write back: progress marks on the diagram ("✓ implemented", "⚠ blocked"), answers next to questions, a new page with their findings. The drawing becomes a live map of the work.

Where I push back

A picture alone is a weak spec. Handing a project session just a PNG makes it re-derive everything, and it will misread things. The value is in the structured meaning: the diagram as a graph, the text transcribed, the ambiguities marked. That's why the package is built by the drawing session, which knows the page, and why "diagram → graph" deserves to be a real tool (it builds on the layout analysis and shape recognition that exist).
Spawning sessions needs guard rails. A new implementation session gets a folder, your usual permissions and a clear first prompt. It should never start silently in the background with write access; it opens where you can see it (a terminal), and the page shows the link.

0.5 Sessions and your system draw for you

The opposite direction of the launchpad: knowledge that lives in sessions, projects and your machine comes onto the canvas, in your hand-drawn style, as material to think with. You've done it already: the fleet architecture pages, drawn with field names that andrew-proj-fd read from the repos.

Linked boards

"New board linked to…" a running session or a project folder (a session is started there if none runs). The link is visible at the top of the page; questions and drawing requests go to that session by default, and it can draw onto the board whenever it has something to show.

A shared diagram description

Sessions don't send prose; they send a small diagram description (JSON: nodes, groups, edges, labels, notes, emphasis). The drawing session lays it out and draws it in your style. The same format comes out of diagram_structure (ink → description), so a hand-drawn diagram can go to a session and come back corrected.

Charts from data, hand-drawn

draw_chart(data, kind, style: hand | clean): bars, lines, pies, gauges, tables, with the axes, labels and title in your handwriting. The system-inspection part ("what CPU, how loaded, how much memory") is Claude Code's own tools; xournalai only needs to draw well.

Refreshable charts

A chart remembers how its data was obtained (the command or question, kept in notes). "Refresh" re-runs it and redraws in place: CPU now versus an hour ago. Snapshots by default, not a live dashboard.

Where I push back

Don't let the drawing session become the project expert. It would read the whole codebase again, costing time and context. It should ask the session that already knows ("give me the module graph as a diagram description") and only draw. That keeps each session small and accurate, and it's exactly what the bus is for.
Live-updating dashboards are scope creep. Continuous redraws fight with your ink and with undo. Snapshots plus a Refresh button (or "refresh every N minutes while I watch", later) give 90% of the value.
Layout is the hard part of "draw the architecture". Twenty nodes and forty edges need a real graph layout (layered, with groups), not the model guessing coordinates. That goes into the app as part of draw_diagram; the model decides what to show, the app decides where.

0.6 The companion session: how the assistant runs (revised)

The defaults. Starting xournalai starts its own Claude Code session, the companion, which serves xournalai and assists you. Other sessions are optional; the companion can connect to them when you ask. With AI switched off in the panel, xournalai is a plain drawing app and the companion stays idle or stopped.

Decided (rev 16): skip stage 1. The first goal is stage 2, the collapsible dock, with the serving session auto-started in its dedicated folder. No GNOME Terminal window.

Three stages of hosting, cheapest first

Stage 1 · Companion terminal (auto-launched)

xournalai opens a terminal window with Claude Code already running in the assistant workspace: MCP connected to this window, skills and CLAUDE.md loaded, a first prompt ("you are xournalai's assistant; serve intents"). It's a real interactive session: a peer on the bus, with voice mode and /mcp, and you can type to it. Days of work; reuses exactly the setup that already works for you.

Stage 2 · Hideable terminal dock

The same companion, but in a terminal panel inside xournalai (VTE, Linux, which is all we need now): show or hide it with a key; the process keeps running while hidden. Tabs: Claude (the companion), plus Codex, OpenCode or a shell, started manually when you want them. No extra windows.

Stage 3 · Structured runner (only if needed)

ACP: fully programmatic control (cancel, permission prompts, token accounting, no terminal at all). Kept on the shelf; we build it only if stages 1–2 hit a real limit.

How in-app controls reach a session running in a terminal

  • Intents over MCP (always works): buttons, the AI pen, your markers and the lasso put intents on the queue. The companion takes them (intents_next), reports progress, and finishes; previews, undo and cancel are the app's. A cancel is seen by the session at its next tool call.
  • A push over the socket bus (better, if spike S5 allows): xournalai posts each intent to the companion as a bus message. An idle session wakes up by itself: no polling loop, and the terminal stays free for you to type.
  • Fallback, a waiting loop: the companion sits in intents_next / wait_for_user (as your canvas session does today); you press Esc to talk to it.

Where I push back

A terminal is a second thing to manage. If it's closed by mistake the assistant is gone. xournalai should watch its companion: show its state in the status strip, offer "Restart companion" (with --resume, keeping context), and never start a second one for the same window.
Interactive sessions ask for permissions. A companion that stops to ask "allow create_from_svg?" breaks the flow. Its workspace settings pre-allow xournalai's tools (and whatever you choose), so it acts without prompts; dangerous things still ask.
Starting it with the app costs a little memory (~300 MB) and some start-up time. Fine on your laptop; offer "start companion: with the app / when AI is switched on / manually".

0.8 Keeping the companion awake: the app watches, the session works

The problem you hit: the session is supposed to watch the canvas all the time, but after a while with nothing to do it stops. That's structural. A model session can't wait for ever: watching today is a loop of wait_for_user calls inside one turn, and the turn ends (your skill even says "after ~2 empty timeouts, stop"). Then nothing wakes it up until you type.

The fix: invert it. xournalai itself is the watcher. It sees every stroke for free and already groups them (work units, markers, AI-pen commands, watch zones). When something meaningful happens, it wakes the idle companion with a short message ("2 new events: a formula at top right, an XC! command on page 2"). The session handles them and goes idle again. Idle is the normal state, not a failure. And it costs less: a model turn only when there's work.

How the app knows the session's state: Claude Code hooks

The companion's workspace configures Claude Code hooks (SessionStart, UserPromptSubmit, Stop, Notification) that report to xournalai's socket with a one-line command: busy, idle, waiting for permission. The status strip shows it, and the app knows when a wake-up is welcome. While it's busy, events are queued; when it goes idle and something is pending, it's woken at once.

How to wake it: three channels, in order of preference

ChannelHowGoodBad
Terminal inputThe companion runs inside tmux (stage 1) or the app's VTE dock (stage 2); the app types a short line into it, as if you had: [xournalai] 2 new events: take them. Uses only public behaviour; works today; simple. Must not collide with your typing: only sent when the hooks say idle and the input line is empty.
Socket-bus messageThe app posts to the companion over the cc-socks bus, like a peer session would.Native wake-up of an idle session; nothing typed into its terminal. Unpublished protocol (spike S5); may change with updates.
Keep-alive via the Stop hookWhen the session tries to stop while watch mode is on, the Stop hook blocks it: "call intents_next again".No external input at all.It burns a turn per timeout even when nothing happens; last resort.

Making it dependable

  • Coalescing: events in the last few seconds go in one wake-up, not one per stroke. The message carries a count and a cursor; details come from intents_next / changes_get.
  • Watchdog: if a wake-up isn't picked up within about 20 s (hooks still say idle, the queue isn't drained), resend once, then show "companion not responding" with a Restart button (--resume, context kept).
  • Quiet hours: AI off or paused means no wake-ups; the queue is kept or dropped as you choose.
  • The skill changes: no more "stop after two timeouts". The companion handles what it's woken for, and ends its turn.
Where I push back on "watching all the time". A session that's always inside a turn, looping on waits, is the fragile and expensive version: it holds a turn open, re-reads context at every timeout, and dies silently. "App watches, session wakes on events" gives the same experience, with fewer tokens, and a clear state you can see in the status strip.

1. Where we started (the first version of the idea)

Kept for the record; sections 0–0.3 describe where the idea is now.

  • Today a separate agent session watches the document over MCP, recognises handwritten commands (XC! revise …) and edits the page. It works, but it's two windows, it needs /mcp reconnects, and it's terminal-only.
  • You want xournalai to carry its own assistant: switch it on, and it does everything the external session does, driven by an AI toolbox, an assistant mode, region buttons and command-writing.
  • A hidden or collapsible terminal inside the app running Claude / Codex / OpenCode would be acceptable to you.
  • External agents over MCP keep working. Personal use first, public later.

2. Critique: where the idea is weak

An embedded terminal is the wrong primary interface. A toolbar button can't reliably drive a text interface: it would have to type into Claude Code's prompt and then work out from terminal output when the agent is done and what changed. There's no structured result, so the app can't preview it, map it to one undo step or offer accept/reject. It also means running a fully privileged coding agent (shell, files, bypassed permissions, a large coding system prompt) to typeset a formula. And VTE is Linux-only in practice.
Revised in rev 11: this argument assumed buttons would drive the terminal. With intents, buttons never touch it: the session reads requests over MCP (or gets them pushed over the socket bus), and previews, undo and cancel live in the app. So a normal Claude Code in a terminal is a fine runner, and the quickest one. See 0.6.
Watching everything with the model costs too much. Every idle pause becomes a full agent turn: 5–60 s and real tokens, although most pauses contain no command. (The answer is in 5.3: watch small work units and pinned zones on the fly, and keep full revision as a manual pass.) The model is also guessing whether ink is a command. Detection must be cheap and certain; only execution should involve the model.
A session per document: right for context, wrong for lifecycle. Agent processes weigh 200–400 MB each. Better: at most one per window, started on first use, stopped when idle, resumed later.
(Later) Public users don't have Claude Code or Codex. An architecture built only on external CLIs serves you, not the public. A built-in backend (API key or local model) must be a swap, not a rewrite.
Reusing the terminal CLIs' voice mode is a trap. Claude Code's (and other CLIs') voice input lives inside their text interface: it only works in the visible terminal, can't be driven through ACP, and it doesn't know what you've selected, where the pen is, or which strokes you just drew. "Make these lines bolder" only works if speech is captured in the app together with the selection and pointer at that moment. Voice must be an app-side layer that produces intents; the CLI's voice mode stays available when you open the session in a terminal.
Many actions don't need an agent. "LaTeXify", "beautify" and "colour this" are single-shot transformations with a known input and output shape: one model call plus a preview. Agents shine at open-ended work. Support both, and don't force the first through the second.

4. Proposal: intents first, then runners

The in-app controls don't talk to an agent. They create intents: small structured requests such as "beautify this selection", "execute the command written with the AI pen here" or "summarize page 3".

It pays off immediately

Your current external session serves intents, so the toolbox works before any embedded agent exists.

One UX for all backends

Preview, accept/reject, undo and cancel live in the app, not in the agent.

The runner is replaceable

Your Claude session through ACP now; other runners later if ever needed.

It reuses what exists

Drafts, EventHub, wait_for_user, pause, permission tiers, notes memory.

5.3 Co-pilot, focused: watch small pieces, revise everything only on request

Your refinement, which I agree with: watching doesn't have to mean the whole page. The co-pilot watches small, fresh pieces of work and leaves full passes to an explicit command. The job per call shrinks from "a whole page" to "these four strokes", so it costs fewer tokens and answers faster.

Work units (automatic)

New strokes are grouped locally, with no model, into units: strokes close in space and time. A unit is closed when you move the pen away to another area, or after an idle period. Only closed units are sent.

Watch zones (pinned)

Lasso a region and choose "Watch this zone" (e.g. the formula block or a diagram). Every change inside it becomes a unit, with the zone's own rule: "LaTeX here", "tidy diagram here". Everything outside is left alone.

Revise (manual, full)

"Revise page" or "Revise selection": a deliberate, strong-model pass for consistency, numbering and style. Runs in the background; the results come back as drafts to review.

What a unit call sends (small on purpose)

  • A crop of the unit at readable resolution, plus its element data (points, bbox).
  • A halo: a thin margin around the unit, so a formula continuing the line above is understood.
  • A tiny page thumbnail for layout, only when the rule needs it.
  • A short text style memory of the page (colours, notation, language, what "XC!" means), kept in notes and not re-derived from images each time.

Rough, to be measured in spike S2: a whole-page turn is roughly 2–5k image tokens plus context and 10–60 s; a unit call is roughly 200–600 tokens and 1–4 s with a fast model. That's about ten times cheaper and faster per reaction.

Rules that keep it pleasant

  • Trigger on "moved on", not only on idle. Moving the pen to another area is a stronger signal that you've finished than a pause, so there are fewer interruptions mid-thought.
  • Hands-off radius: never touch a unit near the pen's current position; you may still be writing it.
  • Local pre-sorting (still no model): the shape recogniser and stroke statistics guess text / formula / drawing, so only the rules that apply are run, with the right prompt.
  • Tiered models: a fast model for small fixes and sorting; strong only for redraws, or when the fast one isn't confident.
  • Each unit is handled once. Unchanged units are never re-sent; editing a processed unit re-queues only that unit.
  • Drafts, in the background: units are processed in a queue while you keep writing; results appear as drafts next to the unit. There's a budget meter and an hourly cap.

The weak spot, and the answer to it

Unit-by-unit editing can lose the global picture: numbering, consistent notation, a diagram referring to a formula. That is what the manual Revise pass and the page's style memory are for. The memory is updated cheaply after each accepted unit, so local calls stay consistent without seeing the whole page.

Modes, then (decided): AI off · AI on with Auto-improve off (markers, commands, buttons, voice only) · AI on with Auto-improve on (the focused co-pilot: fresh pieces and watch zones) · Revise (manual, full pass, any time).

5.8 Voice: talk while you draw

This isn't the existing audio recording. It's a conversational mode: the pen stays in your hand, you talk to the app, and it acts on what you're looking at. Example: select a region, say "make the lines of this part bolder", and it's applied.

How it works

  1. Listening: push-to-talk (a stylus button, a key, the mic button in the AI toolbox), or conversation mode, which listens continuously and detects speech (VAD). A visible mic indicator is always shown.
  2. Context snapshot at speech start: the current selection (ids and bbox), pointer position, visible page region, the strokes of the last few seconds, and the active tool. Pen gestures made while speaking count as pointing: "put it here" plus a tap, or "connect this to that" plus two taps.
  3. Speech-to-text: multilingual; local (whisper.cpp) or cloud; the transcript appears live as subtitles near the pointer.
  4. Intent: the transcript plus the snapshot become an intent, the same queue as the pen, lasso and buttons.
  5. Two lanes:
    • A fast lane for simple edits ("bolder", "red", "undo", "delete this", "zoom in", "next page"): a fast model maps the utterance to one or two tool calls, in about 1–2 s, applied directly.
    • An agent lane for the rest ("redraw this diagram cleanly and label the axes"), which goes through the runner with a draft.
  6. Replies: a short toast by default. Optionally spoken, briefly ("done", "which one: the left or the right box?"). The assistant can ask a clarifying question, and you answer by voice or with a tap.

Why the app and not the CLI

  • Knowing what "this", "these" and "here" mean needs the selection and pointer, which only the app has.
  • It works with every runner (ACP agents, the built-in one, external sessions), because voice is just another intent source.
  • Privacy is a real choice: local speech-to-text is possible.
  • Later, a "live" runner on realtime speech APIs could give sub-second conversation, built on the same intents and tools.

Staging

  • Voice A (early, cheap): push-to-talk dictation into the prompt box, with the selection attached. It reuses intents, so it could arrive right after E7.
  • Voice B: the context snapshot and pen-gesture pointing, the fast lane, subtitles, clarifying questions.
  • Voice C (distant): hands-free conversation (VAD, barge-in, spoken replies), a realtime "live" runner, a wake word.

5.9 Daily-use stability and setup (prototype must-haves)

  • The agent is isolated: it's a child process. If it crashes or hangs, it's restarted and the intent retried or failed cleanly; the UI thread never waits on it.
  • Timeouts and cancel on every intent. Stop always works and leaves no half-applied edits (drafts or a single undo step).
  • Usage limits: if a limit is hit, the status strip says so plainly; switching the runner is manual.
  • Setup check: which CLIs are installed and logged in, and which adapters are present; buttons to install the adapters into the app's private folder; a clear message when a login is needed.
  • One-command install: tools/install.sh builds a release, installs to ~/.local, registers the launcher and sets up the adapters. Updates work the same way.
  • Logs for diagnosis: a runner log per session, and an intent history with timing and outcome.
  • Dogfooding gate: two weeks of your own daily use without a blocker before the pitch build.

5.10 Several Claude sessions and the socket bus

You run several Claude Code sessions on your subscription and let them talk over the local socket bus (/run/user/1000/cc-socks/<pid>.sock; today: xournal-ai-9a, olek-45, andrew-proj-fd). xournalai's assistant should be a citizen of that bus, not a separate world.

What it gives you

  • xournalai's sessions are peers. Each assistant session appears on the bus with a readable name (e.g. xournalai-lecture3). Your other sessions can message it: "draw the architecture of what you just built into my open page".
  • It reaches your other sessions. A Sessions panel lists the local peers and their state; any intent can be routed to a peer. Write "→ @andrew-proj-fd: update the fleet docs from this" with the AI pen, or lasso a region and use Send to session. Replies come back into the document as notes or drafts. This is what you already did by hand between two sessions.
  • Several sessions per document, by role. A light co-pilot session (fast model, the work units) next to a worker session (strong model: Revise, redraws), so a long Revise doesn't block the quick fixes. They share limits, so the status strip shows usage.

How: two channels, deliberately

  • Control channel = ACP (structured: prompts, streamed results, tool calls, cancel, permissions). The app needs this to preview, undo and stop reliably.
  • Peer channel = the socket bus, for session-to-session messages, exactly as your sessions use it today.
The open risk (spike S5). The bus is a Claude Code feature and its protocol isn't a published API: it can change with Claude Code updates. And I don't yet know whether a session launched through ACP (the Agent SDK) joins the bus like an interactive one. Two fallbacks if it doesn't:
  • (a) the app starts Claude Code interactively in a hidden pseudo-terminal, so it's a full bus peer, and drives it through the bus plus MCP;
  • (b) xournalai talks to the bus itself through a small adapter module, isolated so an update to Claude Code breaks one file, not the app.
Decided after S5 with facts, not now.
